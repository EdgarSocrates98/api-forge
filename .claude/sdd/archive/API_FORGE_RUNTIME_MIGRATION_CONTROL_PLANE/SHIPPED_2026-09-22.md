## Lessons Learned

### Process

- Validar a matriz de versões antes do Design evitou inventar uma política Go e explicitou o alvo genérico Python 3.
- Rodar o release gate durante o Build revelou dependências de governança que não estavam no manifest principal: mirrors, playbooks, docs de contrato e schema de knowledge pack.

### Technical

- Contratos Pydantic versionados permitem ligar migração ao TaskSpec e ao verifier sem depender do texto do modelo.
- Representar comandos como propostas de adapters, e não executá-los diretamente, preserva o modo read-only e permite que o sandbox seja a única autoridade de execução.
- O estado conservador REVIEW/BLOCKED é essencial quando toolchain, contratos ou evidências estão ausentes.

### Communication

- As validações incrementais de arquitetura e fluxo reduziram ambiguidades antes do Define e do Design.
- Separar MVP offline/read-only de deploy, AWS e migração de dados manteve o primeiro vertical slice verificável.

### Tools & Libraries

- Pydantic e o registry existente facilitaram contratos fechados e conformance.
- pytest, ruff, mypy e scripts/check_release.py forneceram gates complementares: comportamento, estilo, tipos e integridade do repositório.
- YAML declarativo tornou a matriz extensível e economizou mudanças no supervisor.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Toolchain execution | Conectar adapters aos executors sandbox com allowlist, timeouts, redaction e receipts reais. |
| Mutation evals | Implementar a campanha formal de mutation/holdout e medir o threshold de 95%. |
| API contracts | Integrar diff OpenAPI/gRPC real por finding, bloqueando compatibilidade breaking automaticamente. |
| Data/cloud | Adicionar adapters read-only para Redis, MongoDB, DynamoDB, Neptune, Terraform e AWS dumps. |
| Runtime depth | Expandir regras específicas de Spring/Jakarta, Python packaging e mudanças de stdlib Go. |
| CI | Criar job dedicado para migration analyze/plan/verify e fixtures por versão. |
