## Summary

Foi entregue um control plane read-only e reproduzível para mudanças de API
associadas a Git e CI/CD. O fluxo normaliza um bundle versionado, executa
`analyze -> next-step -> graph -> evidence -> brief`, produz findings,
recomendações, métricas e recibos auditáveis e expõe o mesmo contrato por CLI,
MCP e workflow de CI. A fronteira de segurança permanece explícita: não há
merge, push, dispatch, deploy, comentário, mudança de status ou autofix.

## Lessons Learned

### Process

O manifesto de DESIGN ajudou a tornar a entrega verificável, mas a execução
mostrou que itens de integração precisam declarar desde o início se a prova é
local, replayável ou dependente de um provider externo.

- Manter o BUILD_REPORT como fonte explícita dos resultados e dos gaps evitou
  transformar uma fixture em falsa evidência de produção.
- Reduzir três itens do manifesto por reutilização segura foi válido porque a
  decisão ficou registrada e não alterou o contrato público.
- O próximo ciclo deve reservar uma etapa formal para aprovar política de fork,
  token e freshness antes de coletar receipts live.

### Technical

O desenho bundle-first com transporte injetável manteve o núcleo offline e
permitiu testar GitHub sem SDK nem efeitos externos.

- Erros tipados e códigos `AF-*` produziram falhas CLI/MCP governadas.
- Hashes e receipts demonstram correspondência entre artefatos, mas não
  demonstram por si só autoria, permissão ou verdade operacional do provider.
- `review` e `unresolved` precisam permanecer visíveis; nenhum gap externo
  deve ser convertido em `DONE` por conveniência do pipeline.

### Communication

Definir a fronteira read-only e o significado de “evidência externa” cedo
reduziu ambiguidade entre API, Git, CI/CD, IDE/UI e agents.

- A documentação de suporte deve sempre separar `supported`, `heuristic`,
  `unresolved` e `unsupported`.
- Exemplos completos são úteis, mas devem ser identificados como fixture,
  golden, holdout ou receipt live para não induzir confiança indevida.

### Tools & Libraries

Pydantic, pytest, Ruff e mypy forneceram contratos e gates rápidos. A
`skill-creator` validou a skill específica da plataforma, e a sincronização de
skills/agentes manteve as cópias de execução coerentes.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Provider evidence | Adicionar receipt live reproduzível do GitHub somente após aprovar token, fork e freshness policy. |
| Dataset quality | Versionar exemplos reais anonimizados, com revisão, expiração e hashes verificáveis. |
| Reporting | Adicionar publishers JUnit/Markdown e backend persistente de métricas sem alterar o contrato canônico. |
| IDE/UI | Entregar um host real de IDE/UI que consuma MCP ou artifacts, preservando a projeção determinística. |
| Operations | Provar permissões, deployment, health, custo e rollback em uma fase separada; não inferir esses sinais do replay local. |
