## Summary

The B MVP adds a versioned `ScorecardRoutingAssessment/v1` that classifies eligible routing candidates as champion, challenger or unresolved from explicit local scorecard snapshots. Fresh promoted history can lead inherited risk/complexity ranking, new candidates receive a bounded challenge opportunity, and stale or unresolved history remains visible without becoming champion evidence. The implementation is offline-first, additive to the shipped A contracts and does not execute live shadow work or perform automatic external promotion.

## Lessons Learned

### Process

- Run the release contract gate immediately after registering a new contract; it caught missing documentation before ship and prevented an incomplete archive.
- Keep a final full run on an external pytest basetemp on Windows when tests create Git fixtures; this avoids false repository-state failures.

### Technical

- Explicit lanes preserve governance better than a weighted scalar: freshness and evidence remain states, while objective ranking stays explainable.
- Canonicalizing scorecard snapshots before stable-ID generation makes replay independent of caller collection order.
- Recording challenger metadata without executing it delivers anti-starvation evidence without adding hidden runtime cost or external side effects.

### Communication

- Confirming B as a separate extension after A made it possible to keep risk/complexity authoritative and avoid reopening the MVP A contract.
- Naming live shadow execution and C graph-aware routing as explicit follow-ups prevented them from silently entering this build.

### Tools & Libraries

- Existing Pydantic versioned contracts and the contract registry made additive replay-safe fields straightforward.
- Existing pytest eval-gate helpers enabled the four required case families without introducing a provider-dependent evaluator.
- Ruff, mypy, release gate and SDD spec-linter provided independent verification layers.
